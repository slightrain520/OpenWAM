# 多机开发：代码、环境、数据的三层同步方案

> 学习笔记。适用场景：本地 Mac 修改代码；低配 GPU 服务器（4090）维护已配置的运行环境；按需租用大规模 GPU 服务器执行训练。
> 关联项目：OpenWAM（该仓库已内置本方案中环境层与数据层的完整实现，见第 7 节）。

## 1. 问题定义

多台机器之间需要保持一致的对象可划分为三类，三者的关键属性不同：

| 对象 | 体积 | 变更频率 | 与机器的耦合 |
|------|------|----------|--------------|
| 代码与配置 | MB 级 | 高（每次开发） | 无 |
| 运行环境（CUDA、PyTorch、依赖库） | 5–20 GB | 低（数周至数月） | 与操作系统、驱动、Python 版本强耦合，重装耗时 |
| 数据与模型权重 | 10 GB–TB 级 | 中（按任务更换） | 无（纯文件） |

机器本身的特点：租用服务器生命周期短（用完释放）；机器之间异构（不同云厂商、不同驱动与 CUDA、不同磁盘容量）；网络连通性不确定（部分环境无法直连 GitHub 或 Hugging Face）。

结论：不存在单一手段能同时高效同步三类对象。合理做法是按层选择载体，而不是追求整机克隆。判断标准：换一台新机器，恢复到可运行状态需要几步、多长时间、是否依赖人工记忆。

## 2. 三层分离原则

| 层 | 内容 | 同步载体 |
|----|------|----------|
| 代码层 | 源码、配置、脚本 | Git 仓库 |
| 环境层 | 依赖库与运行时 | 依赖清单重建 / Docker 镜像 / 离线导出包 / 平台实例镜像 |
| 数据层 | 数据集、模型权重、训练输出 | rsync 直连 / 对象存储 / 模型托管平台 |

原理：

1. **按变更频率与体量选择载体。** 代码是小体积高频变更的文本，用 git 的增量对象存储；环境是低频变更的复杂构建产物，用"声明式清单重建"或"镜像分发"；数据是大体量二进制，用支持断点续传的块同步工具。
2. **不可变基础设施（immutable infrastructure）思想。** 环境一旦构建完成即视为只读产物，通过镜像分发到目标机，而不是在目标机上手工逐项安装。手工安装不可复现，也无法审计。
3. **数据与环境分离。** 权重和数据的变更周期与依赖库不同步，混入镜像会导致每次数据更新都重传完整镜像。OpenWAM 的离线交付包即明确排除权重与数据。

## 3. 代码层：Git

基本流程：Mac 上开发并 push，各服务器 pull 后运行。要点：

1. `.gitignore` 必须在项目初期配置，排除数据目录、权重文件与训练输出。OpenWAM 的示例：`/data/*`、`/models`、`*.safetensors`、`*.ckpt`、`outputs/`。原因：git 对二进制文件按全量内容存储快照，误提交大文件后历史会持续膨胀，且清理需要重写历史（rewrite history），代价高。
2. **Git LFS** 的适用边界：仓库内存指针、实体存远端 LFS 存储，适合百 MB 级、数量有限的文件。GB 级权重不建议使用：受存储与带宽配额限制，且拖慢 clone。
3. 提交记录与远程仓库（GitHub 或自建 Gitea）是跨机同步代码的事实标准，无需额外工具。

## 4. 环境层

环境快照有两类实现：**声明式清单**记录"需要装什么"，在目标机重新构建；**镜像**记录"已装好的结果"，直接分发文件系统。

### 4.1 依赖清单（declarative manifest）

| 工具 | 清单文件 | 说明 |
|------|----------|------|
| pip | `requirements.txt` + constraints 文件 | constraints 可锁定传递依赖的版本区间 |
| conda | `environment.yml`（`conda env export` 生成） | 注意：conda 环境目录本身含绝对路径，不可直接拷贝复用，必须由清单重建 |
| uv | `uv.lock` | 解析速度快，锁文件精确到 hash |

优点：文本化、可代码评审、体积 KB 级。缺点：每次构建需网络与时间（分钟级到半小时），且跨操作系统时包版本可能有差异。

### 4.2 Docker 镜像（GPU Linux 服务器的推荐方案）

1. 镜像基于 overlayfs 分层联合文件系统：只读层叠加、写时复制，构建过程逐层缓存。一次构建后，可在任意满足条件的机器上运行（"build once, run anywhere"）。
2. CUDA 职责划分：**宿主机只装 NVIDIA 驱动**；容器内只包含 CUDA runtime/toolkit；由 `nvidia-container-toolkit` 在运行时挂载设备。因此容器内 CUDA 版本与宿主机驱动版本解耦，只要求驱动满足兼容区间。这解决了"不同机器驱动版本不一"这一主要异构问题。
3. 分发：推送到镜像仓库（Docker Hub、GHCR、阿里云 ACR 个人版免费），新机器 `docker pull` 即完成环境恢复，无需构建。
4. 限制：AutoDL 等容器化租用平台不开放宿主 Docker 权限，此类平台改用 4.4 的实例镜像方案。

### 4.3 离线导出包（air-gapped，无外网或受限网络）

原理：`docker save` 将镜像导出为 tar 归档，可 gzip 压缩；配合哈希校验保证传输完整性。

OpenWAM 的实现为 `docker/offline.py`，提供三个子命令：

- `export`：导出镜像归档 + 标准 compose 配置 + 元数据，形成自校验的离线交付包；
- `verify`：仅校验交付包完整性，不加载；
- `load`：在目标机导入镜像。

包内**不包含**权重、数据与输出（见第 2 节原理 3）。目标机前置条件只有：Docker、Compose、NVIDIA 驱动、Python 3.8+。

### 4.4 租用平台实例镜像

AutoDL「保存镜像」、恒源云「备份/恢复」、阿里云/腾讯云「自定义镜像」等，原理为平台侧保存系统盘（可含数据盘）快照，新实例直接以该快照创建。

- 优点：最接近整机快照，环境与数据盘内容一并恢复，操作最少。
- 缺点：快照格式与存储绑定在单一平台，无法跨云迁移；打包与恢复耗时随体量增长。

### 4.5 方案对比

| 方案 | 体积 | 恢复耗时 | 可移植性 | 适用场景 |
|------|------|----------|----------|----------|
| 依赖清单 | KB 级 | 分钟级，需外网 | 高 | Mac、轻量环境、CI |
| Docker 镜像 + 仓库 | 5–20 GB | 分钟级（拉取为主） | 高（需外网） | GPU 服务器主力方案 |
| 离线导出包 | 5–20 GB | 等于传输时间 | 高（免外网） | 内网、受限网络 |
| 平台实例镜像 | 整盘 | 快 | 仅限本平台 | 同平台反复租用 |

## 5. 数据层

原则：大体量文件不进 git、不进镜像；使用支持断点续传与增量校验的批量同步工具。

### 5.1 rsync 服务器直连

- 基于分块校验和做增量传输，仅发送差异部分；`-a` 保留权限与时间戳，`--partial` 保留传输中断的半截文件以支持续传。
- 前提：源机与目标机可同时在线且网络互通（两台服务器直连，或经任一台作中转）。
- 示例：`rsync -a --partial assets/ gpu-host:/path/assets/`

### 5.2 对象存储中转

- 阿里云 OSS、腾讯 COS、S3、Cloudflare R2 等，客户端用 `rclone` 或 `ossutil`。
- 优点：源机释放后目标机仍可拉取；同云厂商租用的实例走内网，带宽高且流量费用低；可作为长期快照。
- `rclone sync` 按 size 与修改时间（可配置校验和）做增量。

### 5.3 模型托管平台

- ModelScope（魔搭）、Hugging Face：面向模型权重的版本化托管，命令行支持断点续传。国内直连 HF 受限时可用 hf-mirror.com 镜像或改用 ModelScope。
- 与对象存储的区别：附带仓库级的版本管理与元数据，适合纯权重文件。

### 5.4 DVC（可选）

数据版本控制工具：git 仓库内记录指针文件（`.dvc` 元数据），实体存放在远端对象存储。适合"数据版本需要与代码版本绑定"的项目。引入额外工具链复杂度，个人项目或数据更替不频繁时可暂不采用。

## 6. 决策流程

换用一台新服务器时的选择顺序：

1. 与此前实例属于**同一平台**且平台支持实例镜像 → 保存镜像 / 克隆实例，恢复成本最低。
2. 否则执行三层恢复：
   - `git clone` 代码；
   - 环境镜像：有镜像仓库则 `docker pull`；无外网则 rsync 离线包后 `offline.py load`；
   - 数据：源机仍在线则 rsync 直连；源机已释放则从对象存储拉取。
3. 将上述步骤固化为 `bootstrap.sh` 或 Makefile 目标，使恢复过程收敛为三条以内命令，不依赖文档外的人工记忆。

## 7. OpenWAM 项目中的落地对照

| 层 | 项目内实现 |
|----|-----------|
| 代码层 | 仓库本体；`.gitignore` 排除 `/data/*`、`/models`、`*.safetensors`、`outputs/` 等 |
| 环境层 | `docker/Dockerfile` + `docker/requirements-cu128.txt` + `docker/constraints-cu128.txt` 构建镜像 `openwam:cu128`；`compose.yaml` 定义运行时挂载；`docker/offline.py` 支持离线导出/校验/加载 |
| 数据层 | `compose.download.yaml` 在线下载 Hugging Face 权重至 `.cache/docker`；`assets/`（约 28 GB 权重与基准数据）通过 rsync 迁移；镜像归档刻意不含权重与数据 |

官方离线交付流程（摘自 `assets/openwam_usage_docs/docker.md`）：

```bash
# 源机（已配置环境）：
make docker-export PYTHON=python3
rsync -a --partial dist/openwam-offline/ gpu-host:/path/to/openwam-offline/

# 目标机（仅需 Docker、Compose、NVIDIA 驱动）：
cd /path/to/openwam-offline
python3 docker/offline.py load . && cp docker/.env.example .env
mkdir -p .cache/docker outputs
```

## 8. 实践要点

1. `.gitignore` 与密钥管理前置：API key、token 既不进 git 仓库，也不打进镜像——镜像的已构建层会永久保留文件，删除后再重新提交无法从历史层抹除。
2. conda 环境目录不可通过 rsync/scp 拷贝到新机复用（内部存在绝对路径绑定），只能由 `environment.yml` 重建。
3. 大文件传输完成后做校验（`sha256sum`，或使用 offline.py 的 verify），断点续传后的文件尤其需要校验。
4. 磁盘容量预估：镜像 + 数据 + 训练输出三者之和；租机时磁盘与 GPU 规格同等重要。
5. 路径参数化：配置使用环境变量（如 OpenWAM 的 `OPENWAM_CACHE_DIR`、`OPENWAM_CHECKPOINT_DIR`），避免硬编码路径造成跨机失效。
6. 训练输出（`outputs/`、W&B 日志）同样属于数据层，应及时回传对象存储；实例释放后本地输出即丢失。

## 9. 术语表

| 术语 | 含义 |
|------|------|
| 不可变基础设施（immutable infrastructure） | 环境构建后视为只读产物；需要变更时重新构建并分发，而非在原环境上就地修改 |
| overlayfs | Docker 使用的分层联合文件系统，多层只读镜像叠加，容器运行时以写时复制（copy-on-write）方式写入独立层 |
| air-gapped | 与公共网络物理或策略隔离的环境 |
| 内容寻址（content-addressable） | 以内容的哈希值定位并校验数据；git 对象、Docker 镜像层、rclone 校验均基于该思想 |
| Git LFS（Large File Storage） | Git 的大文件扩展：仓库内保存文本指针，文件实体存放在独立的 LFS 存储 |
| 声明式清单（declarative manifest） | 以文件形式声明期望状态（依赖及版本），由工具负责在目标机上达成该状态 |
